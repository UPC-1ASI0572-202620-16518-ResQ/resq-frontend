# Estado del frontend para la demostración

Actualizado: 2026-11-12. Los estados describen lo implementado en el frontend actual; no implican una prueba end-to-end contra datos de producción.

| Funcionalidad / ruta | Endpoint utilizado | Estado | Implementación | Cómo probar | Limitaciones |
|---|---|---|---|---|---|
| Login `/login` | `POST /api/v1/authentication/sign-in` y perfil propio | `REAL_FUNCIONAL` | Sesión JWT, interceptor, expiración, carga de perfil y logout. | Iniciar sesión con una cuenta válida y confirmar navegación al dashboard. | Requiere credenciales válidas; no se almacenan contraseñas. |
| Dashboard `/dashboard` | Buildings, Alerts, Incidents, Devices, Monitoring y Connectivity | `REAL_FUNCIONAL` | KPIs y gráficos derivados de lecturas y catálogos reales; “Connected Devices” usa conectividad, no estado administrativo. | Abrir Dashboard tras iniciar sesión. | Los endpoints de Monitoring exponen lecturas actuales, no historia; no se inventan series históricas. |
| Buildings `/buildings` | `GET/POST /api/v1/buildings` | `REAL_FUNCIONAL` | Catálogo, detalle, alta y edición de detalles. | Crear o abrir un edificio. | No existe eliminación de edificio; el control informa el bloqueo. |
| Zones en `/buildings/:buildingId` | `POST /buildings/{id}/zones`, `PUT .../details`, `PUT .../administrative-status` | `REAL_FUNCIONAL` | Alta con código, nombre, descripción y `floorLabel`; edición y activación/desactivación; refresco del catálogo compartido. | Abrir Building Detail, usar **Add Zone**, guardar y comprobar la zona en Spaces. | El piso no es un recurso REST: se agrupa por `floorLabel`. Códigos duplicados dependen de la validación 409 del backend. |
| Spaces `/spaces` y `/spaces/:spaceId` | Buildings/Zones, Alerts, Devices | `REAL_FUNCIONAL` | Zonas reales, dispositivos asignados, alertas y navegación. | Abrir una zona creada desde Building Detail. | Tipo y sensibilidad de zona no forman parte del contrato actual y se muestran como proyección de presentación. |
| Reglas en `Spaces > Monitoring Configuration` | `GET/POST /api/v1/risk-detection/rules`, `PATCH .../{ruleId}/status` | `REAL_FUNCIONAL` | Lista, crea, activa y desactiva reglas globales con confirmación de alcance y aviso de duplicados activos. | Abrir una zona, pestaña Monitoring Configuration. | Las reglas son globales por organización/variable; no existe edición ni perfil por zona. Crear una regla la deja activa según el backend. |
| Devices `/devices` y `/devices/:deviceId` | Device Management, Monitoring y Connectivity | `REAL_FUNCIONAL` | Registro, detalles, capacidades, asignación, estado administrativo, lectura actual y conectividad. | Registrar o abrir un dispositivo y guardar una modificación permitida. | `ACTIVE` administrativo no equivale a `ONLINE`. No existe eliminación física. |
| Floor Plan Editor `/buildings/:buildingId/floors/:floorId/editor` | Catálogos reales + `localStorage` | `LOCAL_DEMO` | Dibujo, imagen (máx. 2 MB), elementos, posiciones de dispositivos reales y restauración local. 2D/3D comparten el modelo del store. | Seleccionar un dispositivo ya registrado, ubicarlo dentro de su zona, guardar y recargar el navegador. | Mensaje visible: “Plano guardado en este navegador; no sincronizado con el servidor”. La colocación visual no reasigna zonas. Se ignoran dispositivos ausentes o inactivos al restaurar. |
| Floor Monitoring `/monitoring/:buildingId/floors/:floorId` | Monitoring, Connectivity, Alerts + plano local | `REAL_FUNCIONAL` | Vistas 2D/3D, lecturas actuales, alertas, conectividad y plano restaurado. | Abrir Monitor desde Building Detail. | Sin histórico consultable; los gráficos solo usan lecturas que el backend realmente devuelve. |
| Alerts `/alerts` y `/alerts/:alertId` | `GET /api/v1/alerts`, Risk Detection evidence, Response Executions | `REAL_FUNCIONAL` | Lista/detalle, evidencia, entrega, acciones y decisiones humanas. Consulta ejecuciones solo para la alerta visible. | Abrir una alerta con acción `PENDING_AUTHORIZATION` y aprobar o rechazar. | `AUTHORIZED` solo confirma decisión; no confirma ejecución física. Las alertas automáticas actuales pueden no traer acciones. |
| Incidents `/incidents` y `/incidents/:incidentId` | Incidents, Monitoring, Connectivity, reglas, Risk Detection y Response Executions | `REAL_FUNCIONAL` | Detalle en cinco secciones, condición actual sin reutilizar la evidencia original, resolución y cierre. Evidencia/acciones solo aparecen con relación confirmada. | Abrir un incidente; resolver uno Active/InProgress con notas; cerrar uno Resolved. | El recurso HTTP no expone `riskDetectionId`, `alertId`, `assignedAt`, `safeAt` ni `resolvedBy`; por ello evidencia/acciones suelen quedar honestamente no disponibles. |
| Asignarme en Incident Detail | `PUT /api/v1/incidents/{id}/assign` | `BLOQUEADO_BACKEND` | Paso visible y explicación del bloqueo; no genera GUIDs. | Abrir un incidente Active. | IAM/Profile usa id entero y el endpoint exige `attendantId` GUID. |
| Condición segura del incidente | Monitoring current + Connectivity + reglas activas | `SOLO_LECTURA` | “Normal” solo con lectura vigente retornada por Monitoring, conexión Online y reglas aplicables; soporta Warning, Critical, Offline, Timeout y Unknown. | Abrir incidente con relación de evidencia confirmada. | Es una evaluación frontend no persistida; el endpoint resolve no valida seguridad IoT. |
| Cierre de incidente | `PUT /api/v1/incidents/{id}/status` con `Closed` | `REAL_FUNCIONAL` | Botón con confirmación solo para estado Resolved. | Resolver y luego cerrar un incidente. | El recurso no expone una fecha de cierre. |
| Búsqueda global | Catálogos cargados reales | `NO_VERIFICADO` | Busca edificios, zonas y dispositivos del store y navega a rutas reales. | Usar la búsqueda del topbar después de cargar el dashboard. | No se ejecutó una prueba manual con sesión autenticada. |
| Settings `/settings` | Profile; Subscriptions existente | `NO_VERIFICADO` | Perfil, contacto, preferencias locales y logout conservados. | Abrir Settings con sesión válida. | Suscripciones están fuera del alcance; el backend observado devuelve 500 y no se añadieron reintentos ni suposiciones. |
| Configuración de API | Base URL + interceptor | `REAL_FUNCIONAL` | Desarrollo y producción usan `https://resq-api-79xy.onrender.com`; `buildApiUrl` evita dobles barras y las rutas incluyen `/api/v1` una sola vez. | Revisar Network al iniciar sesión. | Para backend local se debe cambiar el mecanismo de environment existente; no hay secretos en el repositorio. |

## Respuestas de error

Los gateways convierten fallos HTTP a `ApiError`. Los 404 esperados en recursos opcionales de Monitoring, Connectivity, Risk Detection e Incidents producen estados vacíos/Unknown; 401, 403, 409, 500 y red se muestran como error localizado o snackbar en mutaciones. No se declara una validación end-to-end porque no se usaron credenciales ni datos de prueba autorizados.
